# Souqq

A production-oriented e-commerce marketplace, built as two independent applications: a headless Laravel REST API and a React storefront that consumes it.

## What this is

Most CRUD portfolio projects fall over the moment two people click "buy" at the
same instant. This one was built to survive that, and the test suite proves it.

The engineering weight sits in four places:

| Concern | How it is handled |
| --- | --- |
| **Concurrency** | `SELECT … FOR UPDATE` held inside the checkout transaction, with locks always acquired in ascending product id order so overlapping carts queue instead of deadlocking |
| **Atomicity** | The whole checkout is one `DB::transaction`; a failure injected midway is proven to roll back every write, including the stock decrement |
| **Money** | Never a float. `DECIMAL(10,2)` in MySQL → integer minor units in PHP → a JSON **string** on the wire → integer minor units again in the browser |
| **Cache invalidation** | Attached to Eloquent observers rather than services, so no write path can leave a stale price or stock figure in Redis |

Each is documented with the reasoning, the alternatives that were rejected, and
the tests that prove it — see [`api/docs/`](api/docs/README.md).

## Quick start

### With Docker

`docker-compose.yml` lives in `api/`, so run Compose from there.

```bash
git clone https://github.com/ayobmilad1812001-sys/Souqq.git
cd Souqq/api

cp .env.example .env
docker compose up -d --build
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate --seed
```

The API is then on <http://localhost:8000>.

Five services start: `nginx`, `app` (PHP-FPM), `mysql`, `redis`, `queue-worker`.

> **Not yet verified end to end.** The Compose stack is written to spec but has
> never been built, because Docker was not installed on the development machine.
> The application itself is verified: 141 tests pass, and the migrations and
> seeder run clean.

### Without Docker

You need **two terminals**. The storefront is an empty shell without the API.

**Terminal 1 — the API** (<http://localhost:8000>)

```bash
cd api
composer install

```

```bash

```

> `REDIS_HOST=redis`). Running outside Docker, change both to `127.0.0.1`. If
> Redis is not installed, also set `CACHE_STORE=file` and
> `QUEUE_CONNECTION=database`.

## Architecture

```text
HTTP Request
     │
     ▼
ForceJsonResponse middleware
     │
     ▼
Route + throttle
     │
     ▼
Form Request        validation only
     │
     ▼
Controller          HTTP only, 3-6 lines, no try/catch
     │
     ▼
Policy              who may do this to this record
     │
     ▼
Service             all business logic, transactions
     │
     ▼
Model / Eloquent
     │
     ▼
MySQL
```

If business logic appears in a controller, or an HTTP status code inside a
service, that is a design bug rather than a style preference.

**Observers** sit alongside the models and handle cache invalidation on every
write path. **Events and queued jobs** handle side effects after commit.

## The four hard problems

### 1. Atomic checkout

```text
BEGIN
  │
  ├── lock every product row (ascending id order)
  ├── verify stock against the locked rows
  ├── create the order
  ├── create order items, freezing unit_price
  ├── decrement stock
  └── clear the cart          ← last, and inside the transaction
COMMIT
  │
  └── dispatch OrderCreated   ← after commit only
```

Three ordering decisions matter:

- **The cart is cleared last, inside the transaction.** A failure returns the
  shopper their basket intact instead of leaving them with neither order nor cart.
- **`OrderCreated` is dispatched after commit.** Nothing is worse than a
  confirmation email for an order that rolled back.
- **The Redis queue sets `after_commit => true`,** so a worker on another machine
  cannot pick up a job describing a transaction that has not committed yet.

### 2. Concurrency control

The race being defended against is the classic lost update:

```text
stock = 1

T1: SELECT stock  -> 1
T2: SELECT stock  -> 1      ← T1 has not written yet
T1: UPDATE stock = 0
T2: UPDATE stock = 0
```

Two customers bought the same unit. Stock never went negative, no constraint was
violated, nothing was logged. You find out when the warehouse cannot ship.

The mitigation is `lockForUpdate()` inside the checkout transaction, plus a
deterministic global lock order:

```php
sort($ids);   // every transaction locks in the same order
```

Without that sort, cart `[7, 3]` and cart `[3, 7]` deadlock each other.

There is also a belt-and-braces conditional decrement — `WHERE stock_quantity >= ?`
with the arithmetic evaluated by the database — so that if a future refactor ever
loses the lock, the statement affects zero rows and fails loudly instead of
overselling.

### 3. Money precision

`0.1 + 0.2 !== 0.3`. Across a few hundred line items that becomes reconciliation
failures.

```text
DECIMAL(10,2)  →  Money (integer minor units)  →  JSON string  →  minor units
   database              PHP                        wire            browser
```

Prices are emitted as JSON **strings** (`"249.99"`), never numbers, because a
JSON number would be parsed into a JavaScript float at the last possible moment.

`MoneyTest` adds `0.10` one thousand times and asserts exactly `100.00`.

### 4. Historical price integrity

`order_items.unit_price` is deliberately denormalised — a copy of the price at
the moment of sale:

```text
price at purchase:  100.00
order item stores:  100.00
price today:        120.00
the invoice still says 100.00
```

Foreign keys from `order_items` use `RESTRICT`, not `CASCADE`, for the same
reason: a sold product cannot be hard-deleted, so `ProductService::delete()`
deactivates it instead.

## Roles and authorization

Three roles, enforced in two layers: coarse middleware on route groups, and
per-record policies for ownership.

| | Customer | Seller | Admin |
| --- | --- | --- | --- |
| Browse and search | ✅ | ✅ | ✅ |
| Manage own cart | ✅ | ✅ | ✅ |
| Place and view own orders | ✅ | ✅ | ✅ |
| Review purchased products | ✅ | ✅ | ✅ |
| CRUD **own** products | ❌ | ✅ | ✅ |
| Edit another seller's products | ❌ | ❌ | ✅ |
| View orders containing own products | ❌ | ✅ | ✅ |
| Advance order fulfilment status | ❌ | ✅ | ✅ |
| Cancel any order | ❌ | ❌ | ✅ |
| Manage categories | ❌ | ❌ | ✅ |
| Platform-wide statistics | ❌ | ❌ | ✅ |

### Seller isolation

A seller may only ever touch rows where `products.seller_id === $user->id`. The
rule is expressed **once**, in `ProductPolicy`, and every write path routes
through it:

```php
private function owns(User $user, Product $product): bool
{
    return $user->role->canSell() && $product->seller_id === $user->id;
}
```

Ownership always comes from the authenticated token, never the request payload —
posting `{"seller_id": 99}` produces a product owned by *you*.

Order listings are scoped **in the query**, not filtered in PHP after
pagination, so rows a seller may not see never leave the database.

Two deliberate asymmetries:

- **`CartItemPolicy` has no admin bypass.** Nobody, including staff, edits
  someone else's basket.
- **A seller may advance an order but never cancel it,** because an order can
  contain another seller's goods.

## Order lifecycle

```text
pending ──> confirmed ──> processing ──> shipped ──> delivered
   │            │              │
   └────────────┴──────────────┴──────> cancelled
```

Encoded once, in the `OrderStatus` enum, and unit-tested without a database.

Every order response includes the legal next states, so clients never hard-code
the state machine:

```json
{ "status": "pending", "allowed_transitions": ["confirmed", "cancelled"] }
```

An empty array means the order is terminal.

Cancellation has two paths sharing one implementation: an **admin** may cancel
via the status endpoint, and a **customer** may self-cancel from `pending` or
`confirmed` within `ORDER_CANCELLATION_WINDOW_MINUTES` (default 60). Cancelling
before dispatch restores stock, under the same row locks as a sale.

## API reference

All routes are prefixed `/api/v1`. Authentication is a Sanctum Bearer token.

| Method | Endpoint | Access |
| --- | --- | --- |
| `POST` | `/register` | public · 6/min |
| `POST` | `/login` | public · 6/min |
| `POST` | `/logout` | authenticated |
| `GET` | `/user` | authenticated |
| `GET` | `/categories` · `/categories/{id}` | public |
| `POST` `PATCH` `DELETE` | `/categories…` | admin |
| `GET` | `/products` · `/products/{id}` | public |
| `POST` `PATCH` `DELETE` | `/products…` | seller, admin |
| `GET` | `/cart` | authenticated |
| `POST` | `/cart/items` | authenticated |
| `PATCH` `DELETE` | `/cart/items/{id}` | authenticated |
| `POST` | `/orders` | authenticated · 10/min |
| `GET` | `/orders` · `/orders/{id}` | role-scoped |
| `PATCH` | `/orders/{id}/status` | seller, admin |
| `PATCH` | `/orders/{id}/cancel` | order owner |
| `GET` | `/products/{id}/reviews` | public |
| `POST` | `/products/{id}/reviews` | verified purchaser |
| `DELETE` | `/reviews/{id}` | author or admin |
| `GET` | `/stats` | seller, admin |

Product listings support `search`, `category` (id **or** slug), `min_price`,
`max_price`, `in_stock`, `mine`, `sort` (whitelisted), `per_page` (capped at
100) and `page`.

Checkout is rate-limited more tightly than everything else because each call
opens a transaction and takes row locks.

### Response format

```json
{ "success": true, "data": {}, "message": "Operation successful." }
```

Paginated responses add `meta` and `links` **alongside** `data`, not nested
inside it.

| Code | When |
| --- | --- |
| 200 | OK — **including deletes** |
| 201 | Resource created |
| 401 | Missing or invalid token |
| 403 | Authenticated but not permitted |
| 404 | No such resource |
| 409 | Conflict: insufficient stock, illegal transition, non-empty category |
| 422 | Validation failure or business-rule violation |
| 429 | Rate limited |

Deletes return **200, not 204**: the response envelope requires a body, and a
204 carrying a body is invalid HTTP.

**422 vs 409** is a real distinction. 422 means the request itself is wrong and
an identical retry fails identically. 409 means the request was well formed but
conflicts with current state, and a different retry may succeed. A 409 from the
cart or checkout carries the authoritative figures:

```json
{
  "success": false,
  "message": "Insufficient stock for [Mechanical Keyboard]. Requested 5, only 1 available.",
  "errors": { "requested": 5, "available": 1 }
}
```

Because that exception is raised while holding the row lock, `available` is the
true committed value at that instant.

## The storefront (`web/`)

React 19 + TypeScript + Vite + Tailwind v4, consuming the API over HTTP with a
Bearer token. It shares no code with the API.

```bash
cd web
npm run dev      # dev server on :5173
npm run build    # type-check then bundle
npm run lint
```

Four rules keep the API contract intact:

1. **The response envelope is unwrapped exactly once**, in `src/api/client.ts`.
   No component ever writes `response.data.data`.
2. **Money arithmetic runs in integer minor units**, mirroring the API.
   `parseFloat` on a price is forbidden.
3. **Cart mutations write the response straight into the cache** — every cart
   endpoint returns the complete cart, so refetching would be a wasted trip.
4. **Order actions are rendered from `allowed_transitions`**, so the state
   machine is never duplicated client-side.

Favourites are stored in `localStorage` only; the API has no favourites
resource, and the UI says so rather than implying they sync.

## Testing

```bash
cd api
php artisan test
```

```text
Tests:    141 passed (429 assertions)
Duration: ~8s
```

26 unit tests (money, pricing, the order state machine — no database at all) and
115 feature tests. Roughly half the suite covers **failures**: 403s, 422s, 409s,
rollbacks and race conditions.

The one worth reading is `a_mid_transaction_failure_rolls_back_every_write`. It
injects a failure while the *second* order line is being written — after the
order row, the first line and the first stock decrement have already been issued
— then asserts every one of those writes disappeared.

> **Known limitation, stated plainly.** The suite runs on in-memory SQLite,
> where `lockForUpdate()` is a silent no-op, and PHPUnit is single-threaded. It
> proves the *logic* of oversell prevention, not the *blocking behaviour* of the
> lock. Running it against MySQL is the only way to exercise that:
> `docker compose exec app php artisan test`.

## Continuous integration

GitHub Actions runs on pushes and pull requests targeting `main`, defined in
[`.github/workflows/laravel-ci.yml`](.github/workflows/laravel-ci.yml).

```text
push / pull request → main
          │
          ├── checkout
          ├── setup PHP 8.4 (mbstring, pdo, pdo_mysql)
          ├── start MySQL 8.0 service, wait for health check
          ├── cp .env.example .env
          ├── sed DB_HOST -> 127.0.0.1
          ├── composer install
          ├── php artisan key:generate
          ├── php artisan migrate --force     ← against real MySQL
          └── php artisan test
```

**The `DB_HOST` rewrite matters.** Under Docker Compose, containers reach each
other by service name (`mysql`). On a GitHub runner, Laravel executes directly
on the host while MySQL sits in a container publishing `3306`, so the only
reachable address is `127.0.0.1`.

### What CI does and does not cover

✅ Migrations are validated against **real MySQL**, which catches
MySQL-specific schema problems.

❌ **The test suite itself runs on SQLite, not MySQL.** `phpunit.xml` sets
`DB_CONNECTION=sqlite` before Laravel boots, and Dotenv will not overwrite an
existing environment variable — so `phpunit.xml` wins. The MySQL service is used
only by the `migrate` step, and `lockForUpdate()` is therefore still not
exercised in CI.

❌ **`web/` is never checked.** Because the workflow sets
`working-directory: api`, a TypeScript error or a broken Vite build would pass
with a green badge.

Both gaps, and the fixes for them, are written up in
[api/docs/20-github-actions.md](api/docs/20-github-actions.md).

## Configuration

```env
DB_CONNECTION=mysql
DB_HOST=mysql            # 127.0.0.1 outside Docker
DB_DATABASE=libyamarket
DB_USERNAME=libyamarket
DB_PASSWORD=secret

REDIS_CLIENT=predis
REDIS_HOST=redis         # 127.0.0.1 outside Docker
CACHE_STORE=redis
QUEUE_CONNECTION=redis
SESSION_DRIVER=redis
```

Cache uses Redis database `1` and the queue database `0`, so
`php artisan cache:clear` cannot destroy queued jobs.

Business rules live in `config/marketplace.php` and are environment-driven:

```env
SHIPPING_FLAT_RATE=15.00
SHIPPING_FREE_THRESHOLD=500.00
ORDER_CANCELLATION_WINDOW_MINUTES=60
FRONTEND_URLS=http://localhost:5173      # CORS allow-list
```

Monetary values are read as **strings**, never floats, even in config.

## Docker

```text
        ┌────────────────────┐
        │  nginx:1.27-alpine │  :8000
        └─────────┬──────────┘
                  ▼
        ┌────────────────────┐
        │  app  PHP 8.3-FPM  │
        └─────────┬──────────┘
             ┌────┴────┐
             ▼         ▼
        ┌────────┐ ┌────────┐      ┌──────────────┐
        │ mysql  │ │ redis  │◀─────│ queue-worker │
        │  8.4   │ │   7    │      └──────────────┘
        └────────┘ └────────┘
```

`queue-worker` is built from the **same image** as `app`, with a different
command — so a worker can never run a different revision of the code than the
application that dispatched the job.

Health checks gate startup: `depends_on` alone waits only for the container to
start, not for MySQL to accept connections.

Host ports are deliberately non-standard (`3307` for MySQL, `6380` for Redis) so
the stack does not collide with a local install.

## Project status

**This is a portfolio and engineering-demonstration project. It is not ready to
take real money**, and the reasons are documented rather than hidden.

Known to be missing:

- **No payment gateway.** A search for any payment integration returns only
  `DB::transaction`. The `orders` table has no payment columns.
- **No password reset endpoints.** The config and the `password_reset_tokens`
  table exist; the routes do not.
- **No email verification** — anyone can register with a fake address and become
  a seller.
- **No shipping addresses.** Orders charge shipping but do not record a
  destination.
- **No product images.** There is no image column; the storefront generates a
  stable placeholder tile per product instead.

The full audit — severity, evidence, and a nine-step ordered roadmap — is in
[19-production-gaps-ar.md](api/docs/19-production-gaps-ar.md).

The hard parts are done. What remains is known work, not open engineering
questions.
