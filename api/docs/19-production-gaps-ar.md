## الخلاصة في سطرين

**الأساس الهندسي ممتاز. الوظائف التجارية ناقصة.**

المشروع جاهز تماماً كعرض تقني أو مشروع تخرج، وغير جاهز لاستقبال مال حقيقي —
ليس لأن الكود سيء، بل لأن أجزاء وظيفية كاملة لم تُبنَ أصلاً.

| السؤال | الجواب |
| --- | --- |
| مشروع بورتفوليو / تخرج؟ | ✅ نعم، وبقوة |
| يثبت مستوى هندسي عالٍ؟ | ✅ نعم — القفل التشاؤمي والمعاملة الذرية والدقة المالية |
| يستقبل طلبات ومالاً حقيقياً غداً؟ | ❌ لا |

**التقدير:** الأساس الهندسي ~85٪ · الوظائف التجارية ~55٪

## ما لا يحتاج شيئاً (لا تلمسه)

هذه الأجزاء مبنية بشكل صحيح ومُختبرة، وهي الأصعب في المشروع:

- [x] المعاملة الذرية عند الشراء (`DB::transaction` بسبع خطوات، مع rollback مُختبر)
- [x] القفل التشاؤمي `lockForUpdate()` مع ترتيب أقفال تصاعدي يمنع الـ deadlock
- [x] الدقة المالية: `DECIMAL(10,2)` → كائن `Money` بوحدات صحيحة → نص في JSON
- [x] عزل البائعين متعدد المستأجرين، معرَّف في مكان واحد ومُختبر
- [x] إبطال الكاش عبر Observers يغطي كل مسارات الكتابة
- [x] آلة حالات الطلب معرَّفة في enum واحد
- [x] 141 اختباراً (429 تأكيداً)، نصفها تقريباً لمسارات الفشل
- [x] تحديد معدل الطلبات: 6/دقيقة للدخول، 10/دقيقة للشراء
- [x] ظرف استجابة موحّد ومعالجة أخطاء مركزية

## 🔴 الفئة الأولى: نواقص وظيفية قاتلة

هذه ليست تحسينات — بل أجزاء غير موجودة إطلاقاً.

### 1. بوابة الدفع — **غير موجودة تماماً**

**الدليل:** بحث في `app/` عن أي تكامل دفع أعاد `DB::transaction` أربع مرات فقط.
لا `Stripe`، لا `PayPal`، لا `PaymentIntent`، لا `charge()`.

جدول `orders` لا يحتوي أي حقل يتعلق بالدفع:

```php
$table->id();
$table->foreignId('user_id');
$table->enum('status', ...);
$table->decimal('subtotal', 10, 2);
$table->decimal('shipping_cost', 10, 2);
$table->decimal('total', 10, 2);
$table->timestamp('cancelled_at')->nullable();
```

**لماذا هذا قاتل:** سوق بلا دفع ليس سوقاً. حالياً يضغط العميل "Place order"
فيُنشأ طلب ويُخصم المخزون — **دون أن يدفع شيئاً**.

**المطلوب:**
- هجرة تضيف: `payment_status` (enum)، `payment_provider`، `payment_reference`، `paid_at`
- حالة جديدة في `OrderStatus`: `awaiting_payment` قبل `pending`
- `PaymentService` + webhook endpoint للتأكيد من مزوّد الدفع
- **مهم:** لا يُخصم المخزون نهائياً إلا بعد تأكيد الدفع، أو يُحجز مؤقتاً بمهلة
- اختبارات: دفع ناجح، فاشل، webhook مكرر (idempotency)

**التقدير:** أسبوع

---

### 2. استعادة كلمة المرور — **صفر مسارات**

**الدليل:** بحث في `routes/api.php` عن `forgot-password` أو `password/reset`
أعاد **صفر** نتائج. الإعدادات موجودة في `config/auth.php`:

```php
'passwords' => [
    'users' => [
        'table' => env('AUTH_PASSWORD_RESET_TOKEN_TABLE', 'password_reset_tokens'),
        'expire' => 60,
    ],
],
```

وجدول `password_reset_tokens` موجود في الهجرات — **لكن لا endpoint يستخدمه**.

**لماذا هذا قاتل:** من ينسى كلمة مروره يفقد حسابه نهائياً. لا مخرج.

**المطلوب:**
- `POST /forgot-password` → يرسل رابطاً عبر الطابور
- `POST /reset-password` → يتحقق من الرمز ويحدّث كلمة المرور
- ترقية معدل صارمة عليهما (كِلاهما ناقل لهجمات التعداد)
- إبطال **كل** توكنات Sanctum عند تغيير كلمة المرور
- صفحتان في الواجهة

**التقدير:** يومان

## 🟠 الفئة الثانية: نواقص وظيفية عالية الخطورة

### 3. تفعيل البريد الإلكتروني — غير موجود

أي شخص يسجّل ببريد وهمي ويصبح **بائعاً** فوراً. لا `MustVerifyEmail` على
نموذج `User`، ولا middleware `verified` على أي مسار.

**المطلوب:** تطبيق `MustVerifyEmail`، مسارَا إرسال/تأكيد، وحماية مسارات
البائع بـ `verified`.

**التقدير:** يوم

---

### 4. عناوين الشحن — غير موجودة

الطلب يحسب شحناً بـ `15.00` لكنه **لا يعرف إلى أين يُشحن**. لا جدول عناوين،
ولا حقل عنوان في `orders`.

**المطلوب:**
- جدول `addresses` (المدينة، المنطقة، الشارع، الهاتف، معلَم مميز)
- تجميد نسخة من العنوان داخل `orders` وقت الشراء — كما جُمّد `unit_price`
  بالضبط، وللسبب نفسه: الفاتورة يجب أن تبقى قابلة لإعادة الإنتاج
- ربط تكلفة الشحن بالمدينة بدل الرسم الثابت
- خطوة عنوان في صفحة الدفع

**التقدير:** يومان

---

### 5. صور المنتجات — غير موجودة

لا عمود صور في جدول `products`، ولا رفع ملفات في أي مكان في `app/`.

الواجهة حالياً تولّد **بلاطة متدرجة ثابتة** لكل منتج من رقمه
(`src/lib/productVisual.ts`). هذا حل مقبول للعرض، **لا للبيع** — لا أحد
يشتري منتجاً بلا صورة.

**المطلوب:**
- جدول `product_images` (منتج واحد ← عدة صور، مع ترتيب وصورة رئيسية)
- رفع عبر `Storage` مع تحقق من النوع والحجم
- توليد أحجام مصغّرة في الطابور
- S3 أو ما يكافئه في الإنتاج، لا القرص المحلي
- معرض صور في صفحة المنتج، ورفع في نموذج البائع

**التقدير:** يومان إلى ثلاثة

## 🟡 الفئة الثالثة: إعدادات النشر

سهلة لكنها حرجة. القيم الحالية في `.env`:

```env
APP_ENV=local            ← يجب production
APP_DEBUG=true           ← 🔴 خطر أمني مباشر
APP_URL=http://localhost:8000
LOG_LEVEL=debug          ← يجب error أو warning
DB_CONNECTION=sqlite     ← ملف واحد، لا يتحمّل التزامن
CACHE_STORE=file         ← الكاش المبني على Redis غير مستخدم فعلياً
QUEUE_CONNECTION=database
SESSION_DRIVER=file
MAIL_MAILER=log          ← لا رسالة تصل أحداً
```

### قائمة تحقق قبل النشر

- [ ] `APP_DEBUG=false` — **وحده سبب كافٍ لمنع النشر**. يسرّب مسارات الملفات
      وآثار الاستدعاء وأسماء الفئات لأي زائر يستفزّ خطأ
- [ ] `APP_ENV=production` — يفعّل أيضاً وضع Eloquent غير الصارم
- [ ] `LOG_LEVEL=error`
- [ ] `DB_CONNECTION=mysql` — SQLite ملف واحد؛ **ولن يُختبر القفل التشاؤمي
      فعلياً إلا على MySQL**، لأن SQLite تتجاهل `lockForUpdate()`
- [ ] `CACHE_STORE=redis` و `QUEUE_CONNECTION=redis` — الكاش والطوابير مبنيان
      لـ Redis وحالياً معطّلان عملياً
- [ ] `MAIL_MAILER=smtp` بمزوّد حقيقي
- [ ] `APP_KEY` جديد للإنتاج (لا تُعِد استخدام مفتاح التطوير)
- [ ] HTTPS إجباري + `TrustProxies`
- [ ] معالج طوابير يعمل تحت إشراف (Supervisor أو systemd)
- [ ] `php artisan config:cache route:cache view:cache` في خط النشر
- [ ] نسخ احتياطي آلي لقاعدة البيانات + اختبار **استرجاع** فعلي
- [ ] تتبّع أخطاء (Sentry أو ما يكافئه)
- [ ] `FRONTEND_URLS` يشير للنطاق الحقيقي لا `localhost`

**التقدير:** يوم

### 7. Docker لم يُشغَّل ولا مرة

`docker-compose.yml` و `Dockerfile` مكتوبان حسب المواصفة لكن **لم يُبنيا**،
لأن Docker Desktop غير مثبت على الجهاز. قد يحتويان أخطاء لم تظهر بعد.

**المطلوب:** تثبيت Docker وتشغيل `docker compose up -d --build` مرة واحدة
على الأقل، ثم `docker compose exec app php artisan test` — وهذا يحقق فائدة
مزدوجة: يشغّل الاختبارات على **MySQL حقيقي**، فيختبر القفل التشاؤمي فعلياً.

---

### 8. صفر اختبارات في الواجهة

الـ API فيه 141 اختباراً. الواجهة **صفر**.

**المطلوب:** Vitest + Testing Library للأجزاء الحرجة:
- `money.ts` (اختبارات وحدة — الأسهل والأعلى قيمة)
- `client.ts` وفكّ الظرف وتصنيف الأخطاء
- تدفق السلة والشراء

**التقدير:** يومان

### 9. لا يوجد ErrorBoundary

خطأ واحد غير ملتقط في React ينتج **شاشة بيضاء كاملة** بلا أي رسالة.

**المطلوب:** `<ErrorBoundary>` حول الموجّه مع واجهة احتياطية وزر إعادة تحميل.

**التقدير:** ساعة

## 🔵 الفئة الخامسة: أمور تستحق الانتباه (ليست عاجلة)

| البند | الملاحظة |
| --- | --- |
| التوكن في `localStorage` | قابل للقراءة بأي XSS. مقايضة مقبولة وموثّقة، لكن اعرفها |
| توكنات Sanctum بلا انتهاء | `SANCTUM_TOKEN_EXPIRATION` غير مضبوط — التوكن صالح للأبد |
| البحث `LIKE '%term%'` | لا يستفيد من الفهرس. يحتاج `FULLTEXT` أو محرك بحث عند نمو الكتالوج |
| لا سجل تدقيق للمدير | من غيّر حالة الطلب ومتى؟ يوجد سجل مخزون فقط |
| لا مرتجعات ولا استرداد | الطلب المشحون لا يمكن التراجع عنه بأي شكل |
| لا تعدد لغات | الواجهة إنجليزية فقط — سوق ليبي يحتاج العربية و RTL |
| لا إشعارات حقيقية | `NotifySellersOfNewOrder` يكتب في السجل فقط، بلا قناة فعلية |

## ملاحظة أخيرة

أصعب أجزاء أي سوق إلكتروني — **التزامن، وسلامة المخزون، وذرّية المعاملة،
والدقة المالية** — خلفك بالفعل ومبنية بشكل صحيح ومُختبرة.

ما تبقّى عمل معروف الخطوات، لا مسائل هندسية مفتوحة. هذا موقع جيد جداً
يكون فيه المشروع.
